## 1. ОБЩИЕ СВЕДЕНИЯ И НАЗНАЧЕНИЕ СИСТЕМЫ

### 1.1 Бизнес-цель проекта

Интернет-магазины автозапчастей сталкиваются с проблемой: клиент приходит с артикулом одной марки, но хочет узнать аналоги (кроссы) от других производителей и сравнить цены у разных поставщиков.

**Проблема:**
- Менеджер вручную ищет аналоги в каталогах — долго и с ошибками.
- Цены у поставщиков разбросаны по разным API и прайс-листам.
- Нет единого ответа «вот все аналоги и цены за один запрос».

**Решение (MVP):**
Микросервис, который за один HTTP-запрос:
1. Нормализует артикул.
2. Находит аналоги в локальной БД.
3. Параллельно опрашивает эмулируемых поставщиков.
4. Возвращает единый JSON с аналогами и ценами.

**Ценность для портфолио:**
Демонстрирует навыки: системный анализ, проектирование API, асинхронность, работа с БД, тестирование, Docker, документирование.

---

### 1.2 Границы проекта (Scope)

**Входит в MVP:**
- REST API на FastAPI с одним эндпоинтом `GET /api/v1/search`.
- Локальная БД SQLite с таблицами: `brands`, `products`, `crosses`.
- Модуль нормализации артикулов.
- Модуль поиска кроссов.
- Модуль агрегации цен (асинхронный, timeout 1.5 сек).
- 2 эмулируемых поставщика:
  - Поставщик 1 — REST JSON (мок-сервер).
  - Поставщик 2 — CSV-прайс, загружаемый локально.
- Тесты: PyTest + Postman-коллекция.
- Dockerfile + docker-compose.
- Документация: README.md, TECH_SPEC.md.

**Не входит:**
- Реальные интеграции с поставщиками (только моки).
- Фронтенд / UI.
- Авторизация и роли пользователей.
- Гигантские объёмы данных (БД до 1000 записей).
- Кэширование, очереди, ML.

## 2. ТЕХНИЧЕСКИЕ И ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 2.1 Модуль нормализации артикулов

**Назначение:** привести артикул к единому виду перед поиском.

**Правила нормализации:**

| № | Правило | Пример |
|---|---------|--------|
| 1 | Удалить пробелы в начале и конце | `" 12345 "` → `"12345"` |
| 2 | Удалить внутренние пробелы | `"12 345"` → `"12345"` |
| 3 | Удалить спецсимволы (`.`, `,`, `/`, `\`) | `"12.345"` → `"12345"` |
| 4 | Сохранить дефисы как значимый разделитель | `"90919-01253"` → `"90919-01253"` |
| 5 | Привести к верхнему регистру | `"ik20"` → `"IK20"` |
| 6 | Убрать повторяющиеся дефисы | `"12--345"` → `"12-345"` |
| 7 | Убрать дефис в начале и конце | `"-12345-"` → `"12345"` |

---

### 2.2 Модуль поиска кроссов

**Схема БД (SQLite):**

**Таблица `brands`:**
| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER PK | ID бренда |
| name | TEXT UNIQUE | Название (Toyota, Denso) |
| country | TEXT | Страна |

**Таблица `products`:**
| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER PK | ID товара |
| brand_id | INTEGER FK | Бренд |
| article | TEXT | Нормализованный артикул |
| name | TEXT | Название запчасти |

**Таблица `crosses`:**
| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER PK | ID связи |
| product_id | INTEGER FK | Оригинал |
| cross_product_id | INTEGER FK | Аналог |
| cross_type | TEXT | analog / original / replacement |

**Алгоритм поиска:**
1. Нормализовать входной артикул.
2. Найти бренд по имени (регистронезависимо).
3. Найти товар по (brand_id, article).
4. Если не найден — вернуть 404.
5. Найти все кроссы для этого товара.
6. Для каждого кросса подтянуть данные товара и бренда.
7. Вернуть список аналогов.

---

### 2.3 Модуль агрегации цен (Проценка)

**Назначение:** параллельно опросить поставщиков и собрать цены.

**Требования:**
- Асинхронные запросы (asyncio + httpx).
- Timeout на каждого поставщика: 1.5 секунды.
- Если поставщик упал или не ответил — не ломать общий ответ, а пометить `status: "timeout"`.
- Общий ответ формируется из того, что успело прийти.

**Обработка сбоев:**

| Ситуация | Поведение |
|----------|-----------|
| Поставщик не ответил за 1.5 сек | `status: "timeout"`, `price: null` |
| Поставщик вернул 500 | `status: "error"`, `price: null` |
| Поставщик вернул пусто | `status: "not_found"`, `price: null` |
| Все поставщики упали | Ответ 200, массив цен пуст |
| Один упал, другой ответил | Ответ 200 с частичными данными |

## 3. АРХИТЕКТУРА ДАННЫХ И ИНТЕГРАЦИЯ

### 3.1 Спецификация API

**Эндпоинт:** `GET /api/v1/search`

**Query-параметры:**
| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| article | string | да | Артикул запчасти |
| brand | string | да | Бренд |
| include_prices | bool | нет | Запрашивать ли цены |

**Пример запроса:**
GET /api/v1/search?article=90919-01253&brand=Toyota

**Успешный ответ (200):**
```json
{
  "query": {
    "article": "90919-01253",
    "brand": "Toyota",
    "normalized_article": "90919-01253"
  },
  "original": {
    "id": 1,
    "article": "90919-01253",
    "name": "Свеча зажигания",
    "brand": "Toyota"
  },
  "crosses": [
    {
      "id": 2,
      "article": "IK20",
      "name": "Свеча зажигания",
      "brand": "Denso",
      "cross_type": "analog",
      "prices": [
        {"supplier": "sup1", "status": "ok", "price": 450.00, "currency": "RUB"}
      ]
    }
  ],
  "meta": {
    "crosses_found": 1,
    "suppliers_queried": 2,
    "elapsed_ms": 320
  }
}
Ответ 404 (не найдено):
{
  "detail": "Product not found",
  "query": {
    "article": "00000",
    "brand": "Unknown"
  }
}

### 3.2 Логика эмуляции поставщиков

**Поставщик 1 — REST JSON (мок-сервер):**
- Отдельный FastAPI-сервис на порту 8001.
- Эндпоинт: `GET /api/price?article={article}`
- Эмуляция сбоев:
  - `?fail=timeout` → сервер спит 3 секунды.
  - `?fail=500` → возвращает 500.
  - `?fail=empty` → возвращает пустой ответ.

**Поставщик 2 — CSV-прайс (локальный файл):**
- Файл `data/supplier2_prices.csv`
- Формат: `article,price,currency,stock`

## 6. КРИТЕРИИ ПРИЁМКИ MVP

- API отвечает на `GET /api/v1/search` за < 2 сек.
- Нормализация работает по всем 7 правилам.
- Поиск кроссов возвращает минимум 2 аналога для тестового артикула.
- Агрегатор параллельно опрашивает 2 поставщика.

- Postman-коллекция проходит все 14 кейсов.
- `docker-compose up` поднимает всё с нуля.
